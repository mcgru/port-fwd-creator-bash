# PRD: tun-create.sh — настройка ssh-туннеля между двумя хостами

Документ фиксирует, как понята задача, какие решения приняты и по каким
критериям работа считается сделанной. Версия скрипта: 0.1.0.

## 0. Состав репозитория и статус

    tun-create.sh   скрипт
    PRD.md          этот документ (постановка, решения, критерии, проверки)
    DIALOGUE.md     постановка и переписка, сообщения пользователя дословно
    todo            исходная постановка

Статус на 2026-11-10: реализовано и проверено живьём на парах ggg -> hhh
(openrc) и sss -> ttt (systemd --user, без root). systemd-прогон подтвердил
проброс порта и вскрыл поведение без linger (см. раздел 10). Добавлены
режимы --check и --history и запись истории работы (раздел 6.1), проверены
на обеих парах.

## 1. Цель

Один самодостаточный bash-скрипт, запускаемый с управляющего хоста (ноутбука).
По аргументам командной строки он доводит пару хостов до рабочего ssh-туннеля
и оформляет туннель в постоянный сервис, чтобы тот поднимался сам.

Скрипт не требует ничего, кроме bash, openssh-client и coreutils. Читать
~/.ssh/config и sshd_config он не должен: конфиг разбирает сам ssh.

## 2. Роли и термины

- host1 / u1 — инициатор туннеля. Там живёт ssh-клиент туннеля, ключ и сервис.
- host2 / u2 — приёмник. Там sshd, туда кладётся публичный ключ.
- Контроллер — ноутбук, с которого запускают скрипт. Он ходит по ssh на оба
  хоста и ничего не хранит у себя, кроме самого скрипта.
- Направление — сторона, которая слушает порт. Само ssh-соединение туннеля
  всегда инициируется с host1 на host2.

## 3. Интерфейс

Три позиционных элемента, средний (направление) необязателен:

    tun-create.sh [u1@]host1:ip1:port1 <направление> u2@host2:ip2:port2 [опции]

Направление задаётся опцией или токеном между хостами:

    -L -l --local    >  >>  >>>    }  }}  }}}    слушает host1 (по умолчанию)
    -R -r --remote   <  <<  <<<    {  {{  {{{    слушает host2

Токены с '>' в шелле нужно брать в кавычки, иначе это редирект.

Опции:

    -L, -l, --local        слушать на host1 (по умолчанию)
    -R, -r, --remote       слушать на host2
        --systemd          сервис systemd --user (по умолчанию)
        --openrc           сервис openrc; файлы готовятся у пользователя, ставит root
    -n, --name <имя>       имя сервиса (по умолчанию ssh-tun-<host2>-<port2>)
    -k, --key <путь>       ключ на host1 (по умолчанию ~/.ssh/id_ed25519)
    -o, --ssh-option <список>
                           доп. опции ssh через пробел, каждая станет своим -o
    -K, --ctrl-key <путь>  ключ контроллера для заходов на host1/host2
                           (включает IdentitiesOnly: спасает от MaxAuthTries,
                           когда в агенте много ключей)
    -O, --ctrl-ssh-option <список>
                           доп. опции ssh для заходов контроллера, через пробел
    -f, --force            перезаписать чужой юнит и обновить опции строки ключа
        --teardown, --remove
                           снять сервис на host1 (строку ключа не трогает)
        --check            только проверить, настроен ли туннель (ничего не меняет)
        --history          показать все успешные создания из history.success
    -d, --dry-run          показать план и шаблон сервиса, по ssh не ходить
    -v, --verbose          печатать выполняемые команды
    -h, --help             справка
        --version          версия

История работы пишется на управляющем хосте в ~/.local/share/tun-create/
(XDG_DATA_HOME, если он задан): history.run -- все запуски, history.success --
успешные создания туннелей. Подробности в 6.1.

Разбор адреса: [user@]host[:ip]:port. Обычный случай — IFS=: read.
IPv6 разбирается встроенными средствами bash и пишется в скобках:
host:[::1]:8080. IPv6 без скобок — ошибка с подсказкой.

Пустой ip (host::8080) означает 127.0.0.1.

## 4. Семантика ip:port

Пара 1 описывает сторону host1, пара 2 — сторону host2. Направление решает,
кто слушает:

- -L: слушает host1 на ip1:port1, соединение уходит на ip2:port2 с точки
  зрения host2. В ssh уходит -L ip1:port1:ip2:port2.
- -R: слушает host2 на ip2:port2, соединение уходит на ip1:port1 с точки
  зрения host1. В ssh уходит -R ip2:port2:ip1:port1.

То есть при -R аргументы не переставляются, меняется только сторона
прослушивания. Конфликт направлений (опция -L и токен '<') — ошибка, а не
«кто последний, тот прав».

## 5. Что делает скрипт

1. Разбирает аргументы через getopt, проверяет конфликты, нормализует имя.
2. Разрешает хосты через ssh -G (hostname, port, user). Это нужно, чтобы юнит
   на host1 не зависел от алиасов, которые есть только на ноутбуке. Если для
   host2 в конфиге задан ProxyJump — предупреждает: с host1 он не применится.
3. Определяет менеджер сервисов на host1 до любых изменений. Если запрошен
   systemd, а там openrc (или наоборот), падает и печатает ту же команду
   запуска с дописанным в конец правильным флагом, чтобы скопировать целиком.
4. host1: берёт ~/.ssh/id_ed25519 или создаёт его (ed25519, без пароля),
   возвращает публичную часть в память контроллера. Ключ с паролем — ошибка:
   сервис не сможет его использовать без ssh-agent.
5. host2: делает whoami (реальное имя пользователя уходит в команду туннеля),
   ищет ключ в authorized_keys по телу ключа (не по всей строке, иначе смена
   опций плодит дубли). Нет — дописывает строку
   restrict,port-forwarding,<permit>="ip2:port2"; есть — оставляет как есть,
   а если нужного permit-а нет, предупреждает (--force перепишет опции).
6. host1: первым коннектом на host2 с StrictHostKeyChecking=accept-new
   заполняет known_hosts (идентичность уже проверена на шаге 5).
7. Собирает команду туннеля: -N -T, BatchMode, ExitOnForwardFailure,
   StrictHostKeyChecking=yes, явные UserKnownHostsFile и -i, IdentitiesOnly,
   ServerAliveInterval=30/ServerAliveCountMax=3/TCPKeepAlive (пинг в туннеле
   каждые 30 секунд), доп. -o пользователя (идут первыми, чтобы могли
   переопределить дефолты), -L/-R и u2@канонический_host.
8. Оформляет сервис и пытается его включить (systemd) либо готовит файлы
   (openrc).
9. Проверяет, что порт слушается, и печатает памятку для root блоками через
   пустую строку.

## 6. Персистентность

systemd --user:

- юнит ~/.config/systemd/user/<name>.service (не ~/.local/systemd);
- Type=simple, ExecStart=<ssh> <аргументы>, Restart=always, RestartSec=10,
  After/Wants=network-online.target, StartLimitIntervalSec=0;
- enable/start выполняются от имени u1 (это не root), при недоступной шине
  пользователя включаение остаётся памяткой;
- для автозапуска после перезагрузки root делает loginctl enable-linger u1.

openrc:

- в /etc скрипт не пишет: готовит ~/.local/share/<name>/init.d/<name> и
  ~/.local/share/<name>/conf.d/<name>;
- init-скрипт универсальный, вся команда туннеля в conf.d, запуск через
  supervise-daemon, command_user=u1;
- root ставит файлы, делает rc-update add <name> default и rc-service <name> start.

Памятка всегда содержит: что запустить root-ом, как снять туннель (та же
команда с --teardown), замечание про GatewayPorts для -R на не-loopback
адресе и замечание, что строка ключа в authorized_keys остаётся.

## 6.1 История работы

История живёт на управляющем хосте, в ~/.local/share/tun-create/
(XDG_DATA_HOME, если задан); сами туннели на хостах её не касаются.

history.run -- все запуски, по строке на запуск:

    время  режим  результат  exit  длительность  сервис  направление
    правило  хосты  менеджер  команда

- режим: create, check, teardown, dry-run;
- результат: ok, fail, interrupted (сигнал, код > 128);
- в конце строки -- полная командная строка вызова, а при ошибке ещё и текст
  ошибки после разделителя "|".

history.success -- только успешные создания туннелей:

    время  статус  сервис  направление  правило  хосты  менеджер
    сервисный файл  команда

- статус ok -- сервис systemd запущен и порт реально слушается;
- статус prepared -- openrc: файлы подготовлены, установка осталась за root-ом
  (проверить туннель до установки нельзя, поэтому ok здесь не пишется).

Правила записи:

- историю пишет EXIT-ловушка, поэтому в history.run попадают и аварийные
  выходы через die, и прерывания; help и version не пишутся;
- командная строка нормализуется: токены направления (>, >>, >>>, }, }}, }}})
  и опции -l/--local/-r/--remote заменяются на -L/-R, остальные аргументы
  остаются как были; строка пригодна для копирования в шелл;
- каталог создаётся при первой записи; если создать или писать нельзя --
  предупреждение, сама работа продолжается;
- --history печатает history.success целиком и не принимает адреса хостов;
  если файла нет или он пуст, сообщает об этом.

## 6.2 Проверка: --check

--check ничего не меняет, root не требует и проверяет по тем же аргументам,
что и создание:

1. менеджер сервисов на host1 совпадает с запрошенным (иначе -- готовая
   команда с нужным флагом);
2. ssh-доступ к host1 и host2;
3. ключ на host1 существует и не защищён паролем;
4. строка ключа в authorized_keys на host2: есть, содержит нужный
   permitopen/permitlisten и не ограничена command=...;
5. host2 присутствует в known_hosts на host1 (хэшированные записи тоже
   находятся);
6. сервис: systemd -- юнит есть, enabled и active; openrc -- установлен и
   запущен, либо сообщается, что файлы подготовлены, но ждут root;
7. порт прослушивается на своей стороне.

Итог: число проверок и число проблем. Код возврата 0 -- туннель настроен,
1 -- есть проблемы (каждая строка с "НЕТ" содержит подсказку). Сам запуск
попадает в history.run как режим check. Проверки, которые нельзя выполнить
(хост недоступен, ключа нет), помечаются "инфо" и не считаются проблемой.

## 7. Безопасность и ограничения

- Приватные ключи не покидают хосты, публичная часть живёт только в памяти
  контроллера. На удалённой стороне файлы пишутся с umask 077.
- Аргументы удалённых скриптов экранируются через printf %q: ssh склеивает
  команду в строку, и без экранирования '>' в комментарии ключа становится
  редиректом на той стороне.
- root-действий нет: ни sudo, ни записи в /etc, ни linger.
- Ключ по умолчанию общий (id_ed25519). permitopen/permitlisten сужают его
  до конкретного адреса; для изоляции есть --key с отдельным ключом.
- --teardown не удаляет строку ключа: ключ может быть общим.
- Скрипт не правит sshd_config, не ставит пакеты, не создаёт пользователей.

## 8. Принятые решения

- Конфликт направлений — ошибка.
- Разбор адреса: IFS=: read, для IPv6 — встроенный разбор bash и скобки.
- Направление = кто слушает; соединение всегда host1 -> host2.
- Пустой ip = 127.0.0.1.
- При чужом менеджере сервисов выводится та же команда с нужным флагом в конце.
- Keepalive 30 секунд в ssh-команде.
- Мультипортовость/доп. параметры — опцией -o со списком опций ssh.
- permitopen/permitlisten пишутся сразу.
- Хосты канонизируются через ssh -G.
- Имя сервиса по умолчанию ssh-tun-<host2>-<port2>, переопределяется --name.
- --teardown он же --remove.
- Заходы контроллера на хосты можно сузить до одного ключа: -K/--ctrl-key
  (IdentitiesOnly + -i) и -O/--ctrl-ssh-option. Это нужно, когда в агенте
  больше ключей, чем sshd готов перебрать до MaxAuthTries.
- История работы -- на контроллере, в ~/.local/share/tun-create/: history.run
  для всех запусков и history.success для успешных созданий.
- В историю пишется полная командная строка, направление в ней нормализуется
  до -L/-R (токены >, <<, {, } и опции -l/-r заменяются).
- --check -- только чтение: проверяет конфигурацию и прослушивание порта,
  ничего не меняет и root не требует; --history читает history.success.
- Документы проекта (PRD и лог переписки) хранятся в репозитории.

## 9. Критерии приёмки

1. Скрипт проходит bash -n; help, --version, --dry-run работают без хостов.
2. Конфликт направлений, конфликт --systemd/--openrc, IPv6 без скобок и
   отсутствие порта дают внятную ошибку и ненулевой код возврата.
3. На openrc-хосте без --openrc скрипт падает и печатает готовую команду
   с --openrc в конце.
4. Полный прогон на паре хостов создаёт ключ (если нужно), добавляет строку
   в authorized_keys с permit-опцией, заполняет known_hosts, готовит сервис.
5. Повторный прогон идемпотентен: ключ «уже есть», строка «уже есть с нужными
   опциями», файлы сервиса перегенерируются без ошибок.
6. Туннель реально пробрасывает порт: через поднятую команду приходит
   SSH-баннер целевого хоста.
7. --teardown убирает сервис и подготовленные файлы, строку ключа не трогает.
8. В конце печатается памятка блоками через пустую строку: linger, установка
   openrc-файлов, снятие туннеля.
9. history.run получает строку на каждый запуск (включая ошибки и аварийные
   выходы), history.success -- только на успешное создание; в обоих файлах
   полная командная строка с -L/-R вместо токенов направления.
10. --check на настроенном туннеле даёт все "ok" и код 0, после teardown --
    код 1 с указанием отсутствующего сервиса и порта, и при этом ничего
    не меняет на хостах.
11. --history печатает history.success целиком; если истории нет -- внятное
    сообщение и код 0.

## 10. Как проверялось

Живые тесты на ggg (host1) и hhh (host2), конец 2026-11-10:

- оба хоста ggg и hhh — Gentoo с openrc, поэтому на этой паре systemd-ветка
  не запускалась; там она проверена только статически (systemd-analyze verify,
  шаблон печатается в --dry-run). Живой systemd-прогон сделан отдельно на паре
  sss -> ttt, см. ниже;
- прогон без --openrc упал с подсказкой "../tun-create.sh ggg::18080 \}\}\}
  hhh:127.0.0.1:22 --openrc";
- полный прогон с --openrc создал ключ на ggg, добавил строку
  restrict,port-forwarding,permitopen="127.0.0.1:22" в authorized_keys на hhh,
  заполнил known_hosts и подготовил init.d/conf.d в домашнем каталоге;
- туннель поднят вручную ровно сгенерированной командой: порт
  127.0.0.1:18080 слушается, через него приходит SSH-2.0-OpenSSH_9.8
  от целевого хоста;
- повторный прогон идемпотентен;
- --teardown убрал подготовленные файлы;
- тестовый ключ и его строка в authorized_keys после проверки удалены,
  чужая (ранее существовавшая) строка ключа не тронута.

### systemd, sss -> ttt, без root (2026-11-10)

- sss: systemd, пользователь smelov, XDG_RUNTIME_DIR=/run/user/1003, linger=no.
  ttt: sshd под tun-user, принимает только конкретный ключ.
- Заход контроллера на ttt без явного ключа падал с Too many authentication
  failures: в агенте 12 ключей, а MaxAuthTries на сервере 6. Поэтому добавлены
  -K/--ctrl-key (IdentitiesOnly + -i) и -O/--ctrl-ssh-option.
- Полный прогон без root: ключ создан на sss, строка
  restrict,port-forwarding,permitopen="127.0.0.1:22" добавлена в authorized_keys
  на ttt, known_hosts на sss заполнен, юнит
  ~/.config/systemd/user/ssh-tun-ttt-22.service записан, enable и start
  выполнены от smelov, порт 127.0.0.1:18081 слушается.
- Сквозная проверка: через sss:18081 приходит баннер
  SSH-2.0-OpenSSH_9.6p1 Ubuntu-3ubuntu13.20, то есть проброс до ttt работает.
- Журнал показал поведение без linger: 19:09:23 started, 19:09:36 stopped
  (сессия контроллера закрылась, менеджер пользователя ушёл), 19:09:37 started
  (новая сессия подняла default.target, юнит enabled). То есть без root сервис
  живёт только при активной сессии; автозапуск после перезагрузки требует
  loginctl enable-linger smelov, как и написано в памятке.
- teardown: юнит удалён, is-enabled говорит No such file, порт закрыт.
  Тестовая строка ключа на ttt и созданный на sss ключ после проверки удалены.

### История и --check, sss -> ttt и ggg -> hhh (2026-11-10)

- Прогон sss::18082 -> ttt::22 (systemd, без root) с -K: создание прошло,
  в history.run появилась строка create/ok с командной строкой
  "./tun-create.sh sss::18082 -L ttt::22 -K /home/mcgru/.ssh/id_ed25519"
  (токен }}} заменён на -L), в history.success -- статус ok и путь юнита.
- --check на этом же вызове: 8 проверок, 0 проблем, код 0; юнит enabled и
  active, порт слушается.
- Сквозная проверка проброса: ssh-keyscan с sss на 127.0.0.1:18082 отдал
  ключи ttt.
- После teardown --check дал код 1: юнит отсутствует, порт не слушается,
  остальное (ключ, authorized_keys, known_hosts) по-прежнему ok.
- На ggg -> hhh (openrc) --check корректно нашёл чужую строку ключа с
  command="/bin/true" (проброс не поднимется), отсутствие подготовленного
  сервиса и закрытый порт. Проверка ничего не меняет.
- Найден и исправлен баг проверки known_hosts: ssh-keygen на sss (старая
  версия) не понимает "--", из-за чего -F молча падал и запись ложно
  считалась отсутствующей. После правки хэшированная запись находится.
- Тестовые артефакты (ключ на sss, строка в authorized_keys на ttt) после
  проверки удалены; записи в истории остались как след реальных запусков.

## 11. Найденные нюансы

- На hhh sshd отвечает баннером не сразу: похоже на протокольный
  мультиплексор перед sshd. Проверка «просто прочитать из /dev/tcp» висит,
  а ssh и -W работают. Учитывать при живых проверках.
- У hhh в authorized_keys уже была строка ключа от ggg с command="/bin/true";
  такой ключ туннель не поднимет, но скрипт её не трогает без --force.
- ssh берёт первое значение параметра, поэтому пользовательские -o стоят
  перед дефолтами.
- Без linger systemd --user останавливает юнит при закрытии последней сессии
  пользователя и поднимает его снова при следующей (юнит enabled и висит на
  default.target). Постоянная работа без сессий — только после
  loginctl enable-linger, то есть с root.
- Если в ssh-агенте контроллера много ключей, sshd может ответить Too many
  authentication failures раньше, чем дойдёт до нужного ключа; лечится
  -K/--ctrl-key.
- ssh-keygen старых версий (например, на sss) не принимает "--" после -F:
  молча печатает usage и выходит с нулём. Поэтому в проверке known_hosts
  имя хоста передаётся без "--"; иначе запись ложно считается отсутствующей.
- В истории длительность считается по SECONDS bash, то есть с точностью до
  секунды и от старта скрипта, а не от старта процесса.
